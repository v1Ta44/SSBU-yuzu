# 失焦仍暂停：影片分支遗漏及修正提案（2026-10-26）

状态：用户于 2026-10-26 要求将影片和非影片房间等待时的失焦问题一起修复，已据此实施并更新试用宿主。下文保留提案阶段的调查与对照数据；最终实施和验收边界见 YUZU_BACKGROUND_ROOM_FIX_2026-10-26.md。

## 现场及根因

用户报告当前试用版失焦仍暂停并触发卡住。最新现场 logs/20261026-193929_LAPTOP-D3E75748_play 确认正在运行本轮试用目录，宿主哈希 7c638a7f30658222f2631707b3af65350736ee9908baee54b6ad63569a584c59。环境没有显式 SSBU_FOCUS_NOTIFY，确实使用默认后台策略，不能归为用户开了上游暂停模式。

之前的修复只覆盖游戏通知处理器的一半：

- 游戏 0x71037549e0 后读取焦点状态。状态 2 关闭主循环事件；状态 3 不关闭事件。因此上次将 2 转为 3，只解决了主循环停帧。
- 同一函数在 0x7103754ac8 仍会为状态 3 向游戏广播消息 4。原版影片管理器在 0x71036e3988 附近收到这个标志后暂停影片；恢复前台的消息 2 会启动重新同步、定位和解码恢复。
- runtime/nnmovie_mf.c 现有 SSBU_MOVIE_TEST_RESYNC 注释和原游戏指令均确认这组行为。真实窗口变化会重复触发这条链，主循环可以继续计帧而屏幕中的影片停住。

上次原生回归只模拟主循环事件，完整游戏的可见失焦实验又落在影片分支之外，未覆盖影片正在播放时的暂停 / 恢复。此前“后台运行已修复”的结论不完整，需要补正。

用户现场还记录两次约三秒的无画面间隔，退出码 0；其中启动资源阶段的检测不能全部归因于失焦。本轮确切复现了失焦停播、回前台后仍无新影片帧、反复重新定位，不把这一证据扩大为所有 GPU / 加载卡住都已解决。

## 建议修正

只改 runtime/nnmisc.c 的默认后台适配与必要测试：

1. 默认后台策略下，游戏查询焦点时始终返回运行态 1，而不再返回会触发影片暂停的后台态 3。
2. 真实窗口焦点继续记录为原始状态 1 / 2 / 3，但由于默认策略下游戏可见状态始终为 1，不再向游戏投递无实际状态变化的焦点通知。这同时避免回前台时凭空触发影片重新同步。

继续使用原有 NoSuspend watcher 和退出处理，真实输入归属不改变。显式 SSBU_FOCUS_NOTIFY=1 保留上游完整焦点通知 / 暂停行为，=0 行为保留。不会改第三方插件、资源包、游戏二进制或影片解码产品代码。

这与“只强行让渲染继续”不同：需要阻止默认后台模式下不应发生的游戏自身暂停消息。原始窗口焦点仍可用于诊断与输入判断。
